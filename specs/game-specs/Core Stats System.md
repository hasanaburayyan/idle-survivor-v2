Overview:
The player has four core stats — **Vigor**, **Power**, **Focus**, and **Fortune** — that aggregate contributions from any source (skill tree nodes, equipped items, future structures, buffs, etc.) into per-stat totals. Each minigame reads these totals at runtime and derives its own per-stat values (e.g. the Defensive Battle turns Vigor into starting HP and Power into damage scaling). Stats themselves never appear in gameplay math directly — they are the input layer; minigames own the derivation formulas. The system is a **contract**: any feature can grant stats by writing a row into a single shared `player_stat_source` table, and the totals view updates automatically. This spec only defines the stat layer and contract — concrete grants from the skill tree live in the Intermediate Skill Tree spec, and concrete grants from gear live in the Equipment & Armory rework spec.

User Story:
A player opens their Character panel and sees four stat lines: Vigor 12, Power 7, Focus 3, Fortune 0. Tapping Vigor reveals a tooltip explaining what Vigor governs and a breakdown of where the 12 points came from — "Skill Tree: +5, Armor Vest: +5, Rucksack: +2". They take a new skill point and put it into a "+1 Power" node; the Power line ticks from 7 to 8 instantly, with the breakdown gaining a new row. They equip a different chestpiece; their Vigor line updates the moment the swap finalizes. Later, when they enter a Defensive Battle, the lobby shows their derived starting HP based on current Vigor — not the raw stat, the *value Vigor produces in this minigame*.

Requirements:
+ Server authoritative. All stat definitions, sources, and totals live on SpacetimeDB. The client only renders. Any system that wants to grant a stat does so by writing to `player_stat_source` — never by mutating a "total" directly.
+ A new `stat_definition` table on the server: `statId` (string primary key), `displayName` (string), `description` (string — player-facing one-liner about what the stat governs in general terms), `iconKey` (string — client-side asset key), `sortOrder` (u32). Seeded with exactly four rows in v1: `vigor`, `power`, `focus`, `fortune`. The table exists so future stats can be added by inserting a row, but v1 ships with these four locked in.
+ A new `player_stat_source` table holds every individual stat contribution as one row: `sourceKey` (string primary key), `username` (string), `statId` (string foreign key to `stat_definition`), `amount` (i32 — signed so debuffs are representable later). Indexed by `username` (`accessor: 'player_stat_source_username'`) so per-player aggregation is a single index scan. The primary key is `sourceKey`, which is a deterministic string identifying the source-instance, scoped to a specific player — e.g. `alice:skill:power_minor:vigor` for Alice's Power Minor skill node Vigor contribution, or `bob:equipment:item_inst_42:power` for Bob's equipped item Power affix. The leading `username` segment is mandatory: without it, two players investing in the same skill node would produce identical sourceKeys and silently overwrite each other. Deterministic keys give natural idempotency: re-running a grant for the same player updates the existing row instead of producing duplicates.
+ Source-key naming convention: `{username}:{kind}:{refId}[:{statId}]`. The leading `username` segment guarantees uniqueness across players. The `:statId` suffix is included when one source contributes to multiple stats (one row per stat). Conventions are enforced by callers, not the schema — the schema treats `sourceKey` as an opaque string, but every caller MUST include the player's username as the first segment. Kinds in v1: `skill` (skill tree node), `equipment` (an equipped item instance). Future kinds (`structure`, `buff`, `event`) require no schema change.
+ A private view `myStatTotals` returns one row per stat for the calling player: `{ statId: string, total: i32 }`. Implementation: index-lookup `player_stat_source` by `ctx.sender`'s username, sum `amount` grouped by `statId`, return the four rows (one per `stat_definition`, defaulting absent stats to `total: 0`). Procedural view, but the index lookup keeps re-evaluation cheap — total sources per player are bounded by skill nodes purchased + items equipped, which is dozens at most.
+ A private view `myStatBreakdown` returns one row per source for the calling player: `{ sourceKey, statId, amount }`. Used by the Character panel's tooltip to show "where did my Vigor come from." Same index lookup as `myStatTotals` but no aggregation.
+ Source-management helpers (server-side, not reducers — internal functions called from other reducers):
  - `setStatSource(ctx, sourceKey, username, statId, amount)` — upserts: if a row with `sourceKey` exists, update `amount`; otherwise insert. Callers MUST construct `sourceKey` with the player's `username` as the first segment. Used when a level changes (skill upgrade) or when an item with variable rolls is equipped.
  - `clearStatSource(ctx, sourceKey)` — deletes the row if it exists. Used on item unequip, skill refund (if ever added), buff expiry.
  - `clearStatSourcesByPrefix(ctx, username, prefix)` — deletes all rows for `username` whose `sourceKey` starts with `prefix`. The `username` argument is required so the helper uses the btree index instead of scanning the full table. Used when an item is destroyed (clears all its `{username}:equipment:item_inst_42:*` rows in one call) or a skill node is reset across all granted stats.
  These helpers live in a `stats.ts` module on the server and are imported by the systems that grant stats. They never return data — they mutate `player_stat_source` and rely on the view to recompute.

Derivation contract:
+ Stats themselves are *never used directly in gameplay math by the system*. They are inputs to minigame-specific derivation functions. Each minigame owns its own formulas, defined in that minigame's module on the server.
+ Pattern: at session start (or wherever the minigame needs current stat values), the minigame reads the player's totals via a server-side helper `getStatTotals(ctx, username) → Record<statId, i32>`, then applies its own formulas. Derived values are stored on the minigame's own session/state tables — the stat totals themselves are not snapshotted into minigame tables (the minigame stores the *result*, e.g. `startingHp`, not `vigorAtSessionStart`).
+ Minigames MUST snapshot their derived values at session-start and MUST NOT re-read `getStatTotals` mid-session. A player who equips gear or spends a skill point during an active session does not see those changes reflected until the next session. This keeps minigame outcomes deterministic relative to the moment they began and prevents desync between concurrent participants. If a future minigame design genuinely needs live stat updates, that's a feature decision for that spec — but it's opt-in and must be explicitly justified.
+ Derivation formulas are intentionally not specified here. Each minigame spec defines them. For Defensive Battle, the formulas live in `The Defensive Battle.md`.
+ Stats may have zero effect on a given minigame — that's fine. Overlap across minigames is permitted but not expected; designers can choose any subset of stats per minigame.

Stat semantics (v1 high-level intent — full per-minigame meaning lives in each minigame spec):
+ **Vigor** — survivability. Translates to HP, max charges, damage resistance, or analogous "how much can I take" values.
+ **Power** — offensive output. Scales damage, healing magnitude, action effect strength.
+ **Focus** — control and precision. Scales action quality, timing windows, option-pool size, accuracy.
+ **Fortune** — variance and rewards. Scales loot rolls, crit chance, bonus drops, rare-affix odds.
These descriptions are seeded into `stat_definition.description` so the player sees them in tooltips. They are general-intent only — the exact numeric meaning is per-minigame.

Frontend:
+ A new **Character** panel (location TBD — likely the bottom tab strip alongside Activities / Skill Tree / Equipment, or as a section inside an existing screen) renders the four stats from `myStatTotals` as a vertical list: stat icon, name, total. Stats with `total: 0` still render so players can see what's available to invest in.
+ Each row is tappable. On tap, an inline expansion (or modal) shows the stat's `description` and the per-source breakdown from `myStatBreakdown` filtered to that `statId`. Each breakdown line shows source label + signed amount. Source-label resolution: the client parses `sourceKey` as `{username}:{kind}:{refId}[:{statId}]`, ignores the username segment (it's the calling player), and maps the `kind:refId` portion to a human-readable label — `skill:{skillId}` looks up the skill's display name from `skill_definition`, `equipment:{itemInstanceId}` looks up the item's name from the equipment tables. If a source can't be resolved, fall back to the raw `sourceKey` so nothing silently disappears.
+ Stat totals appearing in *minigame* contexts (e.g. the Defensive Battle lobby showing "Starting HP: 120") are responsibilities of those minigames' UI, not this spec. This spec only owns the Character panel.

Extensibility:
+ Adding a stat: insert one row in `stat_definition`, add seed copy. No other schema changes; the source table and views are stat-agnostic. Whether existing minigames use the new stat is up to each minigame.
+ Adding a new source kind (structures, buffs, etc.): pick a new `kind` prefix for `sourceKey`, call the existing helpers from the new system. No schema changes.
+ Materialized totals (replacing the procedural view with a maintained `player_stat_total` table) is a viable future optimization if profiling shows the view is hot. The helper API stays identical, so the swap is internal — callers don't change. Defer until measured.
+ Debuffs and temporary modifiers (negative `amount`, time-bound sources) are representable today: write a negative-amount row, schedule a cleanup row in the existing scheduler to call `clearStatSource`. No new schema needed for v1.

Migration:
+ This spec adds tables but does not modify or remove existing player data. Players who exist when it ships will have zero `player_stat_source` rows and therefore all-zero stat totals until the Equipment rework and Intermediate Skill Tree ship and start writing rows. That's the intended state — stats genuinely do not exist yet for those players, and the Character panel will show zeros until they earn them.
+ No data migration is required when this spec lands alone. The Equipment & Armory rework spec will define its own migration for in-flight item instances if any have been crafted by then.

Placeholders:
+ The Character panel's exact navigation entry point (new tab vs. section inside an existing screen) is left to the UI Cleanup spec / frontend judgement at implementation time. The data layer is the same either way.
+ Stat icons are placeholders in v1 — `iconKey` exists in `stat_definition` but the client may render a text-only fallback until art is produced.
+ A future "stat caps" concept (max Vigor 999, etc.) is not modeled. Sources can sum to any i32 value. If caps are needed later they belong in the derivation layer (per-minigame), not on the totals.
