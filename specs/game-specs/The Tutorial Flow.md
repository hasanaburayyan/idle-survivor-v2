Overview:
A guided onboarding flow walks new players through the game's earliest mechanics — scavenging, leveling up, spending skill points, discovering resources, and building the Shelter — using obtrusive, click-through popups that the player must acknowledge to dismiss. The flow runs from first signup until the player completes the Beginner Skill Tree, after which it turns itself off and never fires again. Each popup briefly explains a concept, often in-character to reinforce the wasteland-survivor theme, and is paired with a "spotlight" UI element (a highlight, arrow, or dim-everything-else cutout) drawing the player's eye to the next thing they should interact with. The flow is data-driven — every popup is a row in a `tutorial_step_definition` table, and adding, reordering, or rewording a step is a database edit, not a code change.

User Story:
A first-time player signs up and lands on the Activities tab. A popup greets them: "The wastes are quiet today. You'll need scrap to survive — start with what you can find at your feet." The Scavenge button glows. They tap it a few times until they level up. Another popup appears, congratulating them and pointing at the Skill Tree tab, which now has an arrow over it. They navigate there, see the Scavenge Multiplier node lit up, and spend a point. A popup tells them about Parts — the next resource they'll need. They keep playing, each new resource unlock triggering its own popup, until they've unlocked the Shelter and finally maxed every Beginner node. A closing popup tells them the basics are behind them, and the popup system goes silent.

Requirements:
+ Server authoritative. All tutorial state lives on SpacetimeDB. The client never decides which popup to show — it asks the server, renders what comes back, and reports back when the player dismisses it.
+ A new `tutorial_step_definition` table on the server: `stepId` (string primary key), `sortOrder` (u32), `prereqStepId` (string — empty for the first step, otherwise references the step that must be completed before this one becomes eligible), `triggerCondition` (tagged union — see below), `headline` (string — bold short title), `body` (string — supports newlines), `primaryCtaLabel` (string — e.g. "Got it", "Begin", "Continue"), `spotlightTargetKey` (string — empty if no spotlight; otherwise a key the client maps to a UI element ref), `tone` (tagged union with variants `inCharacter` and `meta` so styling can vary slightly between flavor-text and instructional popups).
+ `triggerCondition` is a tagged union with variants:
  - `chained` — fires the instant `prereqStepId` is completed. Used for popup chains where one dismissal flows into the next.
  - `playerLevelAtLeast` carrying `level: u32` — fires when `playerState.playerLevel >= level` and prereq is completed.
  - `skillPurchased` carrying `skillId: string`, `minLevel: u32` — fires when the player has a `player_skill` row at or above the given level.
  - `activityPerformed` carrying `activityId: string`, `minTimes: u32` — fires when the player has performed the activity at least N times (`player_activity.timesUsed >= minTimes`).
  - `treeCompleted` carrying `treeId: string` — fires when the named skill tree's completion rule is satisfied.
  - The variant list is extensible. Add a variant only when an existing one can't express the trigger you need.
+ A new `player_tutorial_progress` table holds (username, stepId, completedAt) — one row per step the player has dismissed. Indexed by username. Absence of a row for a stepId means it's still pending.
+ A private view `myActiveTutorialStep` returns at most one row of `tutorial_step_definition`: the lowest-sortOrder step that is (a) not completed by the player, (b) has its `prereqStepId` either empty or completed by the player, and (c) has its `triggerCondition` satisfied. The client subscribes to this view and renders a popup whenever it returns a row; otherwise no popup is shown.
+ Reducers:
  - `completeTutorialStep({ stepId })` — validates the step is the player's currently-active step (mismatch throws), inserts a `player_tutorial_progress` row stamped at `ctx.timestamp`. The next dismissal-or-trigger naturally surfaces the next eligible step on the next view evaluation.
  - `skipTutorial()` — inserts a `player_tutorial_progress` row for *every* `tutorial_step_definition` row the player hasn't already completed. Hard kill switch for players who don't want the guided flow. Surfaced as a small "Skip tutorial" link on every popup.
+ Tutorial off-switch: once the player has completed the final step (the closing popup, which is itself triggered by `treeCompleted("beginner")`), `myActiveTutorialStep` returns nothing for the rest of the player's life. No further popups, no new steps appearing for an existing account when the team adds tutorials for later content — those would have to be a separate "intermediate tutorial" with its own table or scope marker.

Spotlight system:
+ The client holds a `SpotlightTargetRegistry` (a React context keyed by `spotlightTargetKey` strings, mapping to a ref + bounding rect via `onLayout`). UI components that might be a tutorial target — the Scavenge button, the Skill Tree tab, individual skill nodes, the Shelter activity — register themselves under stable keys.
+ When the active tutorial step has a non-empty `spotlightTargetKey`, the popup overlay renders a dim layer covering the screen with a cutout (rounded rect with a small padding) over the registered target, plus a glowing border and either an arrow or a pulsing outline. Tapping the spotlight target itself is allowed (so the player can take the action being highlighted) — every other interaction is blocked while the popup is up.
+ If the spotlight key isn't registered (e.g., the target lives on a tab the player isn't currently viewing), the overlay renders the popup without a cutout but with a hint indicating where to navigate (e.g. "Open the Skill Tree tab"). v1 can be coarse here: just show the popup on top of whatever the player's looking at, no cutout, with body copy that names the destination.

Popup UI:
+ A modal `TutorialPopup` overlay renders on top of every other surface — above tabs, above the bottom group panel, above the notifications tray (closes any open tray on appear), above the minigame modal. The notifications bell and tray are non-essential during tutorial; the minigame modal is unlikely to be open during early-game tutorial steps but if it ever is, the tutorial yields to it and resumes once the minigame closes.
+ The popup itself: a centered card with a tinted backdrop, the step's `headline` in bold, the `body` text below, and a single primary CTA button labeled with `primaryCtaLabel`. A small "Skip tutorial" link in a corner. No close-button-without-acknowledgment — the player must press the CTA (or skip).
+ Pressing the CTA fires `completeTutorialStep`. The popup unmounts as soon as the view stops returning the step (i.e., after the reducer round-trip). Brief loading state while the reducer is in flight.
+ Tone styling: `inCharacter` popups get a slightly aged, parchment-y feel (off-white background, serif-leaning font if available); `meta` popups get the regular UI treatment. Both styles are simple Tailwind class swaps in v1 — fancier styling can come later.

Tutorial step list (v1 seed):
The seeds below are the initial Beginner-tree-aligned tutorial. Each step's `prereqStepId` chains to the previous one unless otherwise noted. Body text is illustrative; copy can be tuned without touching code.

1. `welcome` — `triggerCondition: chained` (no prereq, fires immediately after first signup). Tone: in-character. Headline: "The wastes." Body: "It's quiet for now. You're going to need scrap — bottle caps, scrap metal, anything that survived. Start by scavenging at your feet." Spotlight: none. CTA: "Begin."
2. `try_scavenge` — chained. Tone: meta. Headline: "Scavenge." Body: "Tap the Scavenge button to gather scrap. Keep tapping — every press counts." Spotlight: `activity_button:scavenge`. CTA: "Got it."
3. `first_level_up` — `triggerCondition: playerLevelAtLeast(1)`. Tone: in-character. Headline: "You're learning." Body: "All that scavenging taught you something. You earned a skill point — somewhere out there, you should figure out how to spend it." Spotlight: `tab:skill_tree`. CTA: "Show me."
4. `first_skill_spend` — `triggerCondition: chained`. Tone: meta. Headline: "Spend your point." Body: "A skill point is yours to spend. Tap Unlock Parts — it opens the next resource and starts the chain that follows." Spotlight: `skill_node:unlock_parts`. CTA: "Continue." Note: the `scavenge_multiplier` skill referenced by an earlier draft of this spec was removed when multiplier nodes moved to the Intermediate tree, so this step now uses a `chained` trigger and spotlights the first real Beginner pick (`unlock_parts`) instead.
5. `unlock_shelter_taken` — `triggerCondition: skillPurchased("unlock_shelter", 1)`. Tone: in-character. Headline: "Shelter, in theory." Body: "You unlocked the Shelter. That puts a Build Shelter activity on the Wastes — once you've built it, you can travel inside. There's room in there for a Workbench, and a Workbench will eventually automate your scavenging while you focus on bigger things." Spotlight: none. CTA: "Got it." Note: this step has the same `prereqStepId` as `unlock_parts_taken` (both chain off `first_skill_spend`); whichever skill the player buys first surfaces its popup first.
6. `unlock_parts_taken` — `triggerCondition: skillPurchased("unlock_parts", 1)`. Tone: in-character. Headline: "Parts." Body: "Bolts, gears, broken machinery. Worth more than scrap to anyone who can fix things. There's a new activity in the Wastes for finding them." Spotlight: none. CTA: "Got it."
7. `unlock_metal_taken` — `triggerCondition: skillPurchased("unlock_metal", 1)`. Tone: in-character. Headline: "Metal." Body: "Heavier than scrap and harder to come by. Useful for building." Spotlight: none. CTA: "Got it."
8. `unlock_fabric_taken` — `triggerCondition: skillPurchased("unlock_fabric", 1)`. Tone: in-character. Headline: "Fabric." Body: "Scraps of cloth and tarp. People will need it before the cold." Spotlight: none. CTA: "Got it."
9. `unlock_food_taken` — `triggerCondition: skillPurchased("unlock_food", 1)`. Tone: in-character. Headline: "Food." Body: "Canned. Mostly. You'll learn to take what you can." Spotlight: none. CTA: "Got it."
10. `unlock_meds_taken` — `triggerCondition: skillPurchased("unlock_meds", 1)`. Tone: in-character. Headline: "Medicine." Body: "Painkillers, antibiotics, the occasional miracle. You've found nearly everything this stretch of wastes has to offer." Spotlight: none. CTA: "Got it."
11. `shelter_built` — `triggerCondition: activityPerformed("build_shelter", 1)`. Tone: in-character. Headline: "Shelter, built." Body: "Walls, a roof, a place to keep what you've gathered. Travel here when you can — the Workbench you build inside is where automating your scavenging starts." Spotlight: `tab:travel`. CTA: "Got it."
12. `beginner_complete` — `triggerCondition: treeCompleted("beginner")`. Tone: meta. Headline: "Beginner skill tree complete." Body: "Resources mapped. Shelter standing. Open your Character tab next — your stats are the spine of classes, battles, and everything that follows." Spotlight: `tab:character`. CTA: "Show me." (This step intentionally points at the next horizon — the stat system and class unlocks — rather than ending the tutorial silently.)

Extensibility:
+ Adding a tutorial step is one row in `tutorial_step_definition`. No client code changes unless the step needs a new `triggerCondition` variant or a new `spotlightTargetKey` that doesn't have a registered UI target yet — in which case the missing piece is small and local.
+ Future content (Intermediate Skill Tree, class trees, the Defensive Battle, etc.) can have its own tutorial flows by seeding new steps. Whether they live in this table or get partitioned into separate tables (e.g. `intermediate_tutorial_step_definition`) is a design choice for when that content ships; this spec doesn't preempt it.
+ Localization is out of scope for v1 — `headline` and `body` are stored as raw strings. Adding a `localeKey` column later, with strings looked up from a localization table, is non-breaking.

Placeholders:
+ The spotlight cutout system can be coarse in v1 — a dim layer with a glowing rectangle around the target is enough. Pulsing arrows, animated borders, and other polish can come later. The data model already carries `spotlightTargetKey`, so upgrades are visual only.
+ The "Skip tutorial" link's confirmation dialog ("are you sure?") is recommended but not required — v1 can ship with a single-tap skip and add the confirmation later if support requests pile up.
+ If the player signs up before this spec ships and reaches the game with the tutorial-eligibility condition met (e.g., already completed Beginner), they should *not* retroactively see the closing popup. The `myActiveTutorialStep` view's "step not completed and trigger satisfied" rule will surface every step they technically haven't completed yet — which is *every* step, including ones whose triggers are already true. To prevent that, when the spec ships, write a one-shot migration reducer that inserts `player_tutorial_progress` rows for every existing player against every step (effectively skipping the tutorial for legacy accounts). New accounts created post-ship start with no progress rows and see the tutorial normally.
